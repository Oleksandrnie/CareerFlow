# CareerFlow UI Refresh — техническое задание

- Статус: согласовано к реализации
- Ветка: `codex/ui-refresh-impeccable`
- База: чистый `dev`, commit `d819eb1`
- Дата подготовки: 2026-11-05

## 1. Цель и результат

Обновить внешний вид и удобство существующего интерфейса CareerFlow, сохранив проверенные пользовательские сценарии и локальный характер приложения. Результат — единая, контрастная и адаптивная система экранов для ведения поиска работы: от добавления вакансии до резюме, ATS, интервью и аналитики.

Дополнительно исправить сообщённый баг: при смене светлой/тёмной темы пользователь должен оставаться на том же разделе и экране, не теряя открытое состояние или несохранённый ввод.

## 2. Пользователи и режим поверхности

Основной пользователь — один кандидат, который ведёт несколько процессов поиска работы и возвращается к ним с desktop, tablet или телефона. Главные задачи:

- быстро добавить вакансию и понять её текущий статус;
- подготовить и сохранить отдельную версию резюме, сопоставить её с вакансией;
- записывать интервью, заметки и файлы;
- видеть динамику процессов поиска.

Это интерфейс режима **Operate** из Impeccable: пользователь выполняет конкретные действия в рабочем пространстве. Приоритеты — ясность структуры, сканируемость, предсказуемая навигация и удобная работа с плотными данными, а не рекламная подача.

## 3. Исходное состояние

Подтверждено по исходникам:

- приложение — vanilla JavaScript SPA: `careerflow/static/index.html`, `app.js`, `app.css`;
- верхняя навигация содержит «Вакансии», «Главное резюме» и «Аналитика»;
- у вакансии семь вкладок: Overview, Resume, ATS, AI / Codex, Timeline, Notes, Files;
- уже есть английский и русский интерфейс, светлая и тёмная темы, мобильный drawer списка вакансий, сохранение последней вакансии и её вкладки;
- CSS содержит несколько последовательных переопределений общих правил и breakpoints; некоторые цвета заданы напрямую, а `--accent` для AI-оценки не определён;
- responsive-тесты частично проверяют текст CSS регулярными выражениями, поэтому сами по себе не подтверждают геометрию в браузере.

Источники для реализации: [app.css](../careerflow/static/app.css), [app.js](../careerflow/static/app.js), [responsive UI tests](../tests/test_responsive_ui.cjs), [SPA workflow tests](../tests/test_spa_workflows.cjs).

## 4. Визуальное направление

Рекомендуемая гипотеза по пожеланию пользователя:

- светлая основа экранов;
- чёрный или графитовый текст и заметные тёмные элементы;
- более выразительный современный цветовой акцент вместо обязательного зелёного;
- существующий переключатель тёмной темы остаётся доступен и получает согласованную палитру;
- точный акцент не фиксируется заранее: перед общей стилизацией сравнить 2–3 компактных варианта на одном рабочем экране с одинаковыми синтетическими данными и состояниями.

Обновление трактуется как визуальная эволюция рабочего приложения, а не смена продуктовой архитектуры. Не добавлять декоративный цвет ради цвета: статусы, ошибки, подтверждения и показатели должны использовать понятные семантические роли. Дизайн не должен выглядеть как набор вложенных карточек.

## 5. Объём работ

1. **Дизайн-основа.** Упорядочить CSS-токены для светлой и тёмной темы: фон, поверхности, основной/вторичный текст, акцент, границы, фокус, статусные цвета, графики, размеры текста, интервалы, радиусы и тени. Устранить несуществующие переменные и непреднамеренные жёстко заданные цвета.
2. **Общий каркас.** Согласовать шапку, глобальную навигацию, список вакансий, область содержимого, мобильный drawer и состояния активного раздела.
3. **Рабочее пространство вакансии.** Чётко разделить идентификацию вакансии, статус, основное действие и второстепенные действия. Сохранить семь существующих вкладок и их сценарии; длинные заголовки должны быть доступны без наведения мыши.
4. **Остальные поверхности.** Привести к общей системе Master Resume, ATS, AI / Codex, Timeline, Notes, Files, Analytics, формы импорта, редактирования и диалоги подтверждения.
5. **Состояния интерфейса.** Согласовать пустое, загрузочное, успешное, ошибочное, disabled, архивное и подтверждающее состояния. Ошибка должна объяснять следующий шаг и сохранять пользовательский ввод.
6. **Доступность и адаптация.** Проверить работу с клавиатуры, фокус, ARIA-состояния, длинные русские строки, уменьшенное движение, масштабирование и узкие экраны.
7. **Финишная проверка.** Провести визуальную проверку основных экранов в обеих темах и локалях на синтетических данных; при необходимости обновить существующие UI-тесты под выбранную семантическую структуру.

## 6. Баг переключения темы

Пользователь сообщил, что после переключения темы текущая страница сбрасывается на главную. В исходнике `setTheme()` обновляет тему документа и localStorage без явного перехода; перезагрузка страницы находится в отдельной ветке смены локали на английский. Причину следует воспроизвести и найти во время реализации, не делать предположений по одному обработчику.

Критерии исправления:

- тема меняется без перехода на другой раздел и без полной перезагрузки приложения;
- сохраняются текущий глобальный раздел, выбранная вакансия, активная вкладка, положение прокрутки, открытая форма/диалог и несохранённый пользовательский ввод;
- выбранная тема остаётся сохранённой после ручной перезагрузки;
- критерий проверяется из Analytics, Master Resume и каждой вкладки вакансии, а также во время ввода в форму.

## 7. Функциональные и архитектурные границы

Обновление UI не меняет API, backend, сервисы, SQLite-схему, правила импорта, ATS-алгоритм, аналитику и политику хранения данных. Существующая функциональность должна оставаться доступной:

- импорт вакансии из текста, поддерживаемого файла или публичной HTML-страницы с просмотром описания до подтверждения;
- явный выбор пользователя перед запуском Codex и сохранение результата только по его действию;
- этапы и архив вакансии, экспорт и безопасная политика удаления с CV;
- неизменяемые версии резюме, связь версий с источниками и привязка к вакансии;
- ATS-анализ с сохранением использованных версий резюме и описания вакансии;
- структурированные события, интервью, заметки и локальные вложения;
- существующая семантика метрик и фильтров аналитики.

Не менять ключи browser storage без обоснованной миграции. Сохранить контракты `careerflow-theme`, `careerflow-locale` и `careerflow-last-vacancy-navigation`, а также существующие `id`, `data-*` селекторы и устойчивые ожидания тестов либо обновлять их вместе с поведением.

Не добавлять CDN, внешние шрифты, удалённые ресурсы, облачную синхронизацию, телеметрию, новые бизнес-функции, Kanban, новые аналитические метрики, изменение ATS, авторизацию или замену frontend-стека. Данные пользователя не должны покидать локальное приложение в результате UI-обновления.

## 8. Критерии приёмки

- **Цвет и темы:** в светлой теме есть светлые поверхности, чёрный/графитовый текст и утверждённый выразительный акцент; тёмная тема использует отдельные подходящие значения токенов. Контраст текста и фокуса проверен, цвет не является единственным способом показать состояние. Ни один стиль не ссылается на неопределённый токен.
- **Единообразие:** заголовки, кнопки, поля, карточки данных, статусы, диалоги, пустые состояния и уведомления имеют согласованную визуальную иерархию; важные действия визуально отделены от редких и опасных.
- **Навигация и поведение:** смена темы выполняет критерии раздела 6. Переключение между глобальными разделами, выбор вакансии и вкладок, возврат к последнему экрану и закрытие drawer не теряют выбранное состояние.
- **Локализация:** все служебные подписи, placeholders, подсказки, aria-label, сообщения об ошибках и новые состояния доступны на английском и русском. Пользовательский текст вакансий, резюме и заметок не переводится и не переписывается автоматически.
- **Адаптивность:** основные действия работают на ширинах 320, 390, 768, 1024 и 1440 px и при увеличении масштаба. Нет горизонтальной прокрутки всей страницы; внутренняя прокрутка списка, вкладок, этапов или таблиц допустима, если она заметна и доступна с клавиатуры. Длинные названия, файлы и русские подписи не перекрывают соседние элементы.
- **Доступность:** интерфейс полностью проходим клавиатурой; фокус заметен; состояния выбранных вкладок и drawer имеют доступное представление; диалоги имеют имя, понятный начальный фокус и возвращают фокус после закрытия; закрытые панели исключены из случайной навигации.
- **Устойчивость:** ошибка сети/импорта не стирает введённые данные; повторный submit не создаёт дубликаты; запоздавший ответ не заменяет экран другой вакансии или вкладки.
- **Local-first:** UI работает без внешнего запроса шрифтов, изображений, скриптов или стилей; пользовательские данные не отправляются наружу автоматически.
- **Проверяемость:** тесты подтверждают пользовательское поведение, а ручная браузерная проверка подтверждает реальную геометрию экранов и тем.

## 9. Последовательность реализации

1. Зафиксировать текущие экраны и контрактные сценарии на синтетических данных; воспроизвести проблему со сменой темы.
2. Сравнить несколько компактных цветовых вариантов; выбрать направление до раскатки на все экраны.
3. Обновить токены и общие компоненты, затем каркас и мобильную навигацию.
4. Последовательно применить систему к вакансии и семи вкладкам, затем к Master Resume, Analytics и общим формам/диалогам.
5. Исправить сброс состояния при смене темы, сохранить контекст текущего экрана и добавить регрессионное покрытие.
6. Проверить длинный текст, локализацию, контраст, фокус, responsive-состояния и уменьшенное движение; устранить обнаруженные нарушения и выполнить визуальную полировку.

## 10. Валидация реализации

После реализации выполнить полный набор CareerFlow из корневого `AGENTS.md`: compileall, полный `unittest`, проверку JS-синтаксиса и четыре UI-сценария (`analytics`, `ats`, `responsive`, `spa_workflows`). Для визуальной проверки запустить приложение только с временными SQLite и storage путями и синтетическими данными. Проверить пустое состояние, длинные поля, формы, ошибки, несколько CV-версий, обе темы/локали и смену темы с каждой страницы. Не использовать рабочие `data/` и `storage/`.

В этом ТЗ-таске проверки приложения не запускались: код не менялся. Тестовый и браузерный прогон относится к последующей реализации.

## 11. Как применены материалы Impeccable

Impeccable v4.8.0 содержит основной skill с 24 командами (команда `craft` устарела) и справочными playbook-файлами; в репозитории также есть CLI-детектор, hooks, live-режим и конфигурации для нескольких coding tools. Для этой задачи применена схема `shape`: определить режим поверхности, задачи пользователя, направление, границы и проверяемый результат до написания UI-кода. Для реализации подходят `document`/`extract` (система компонентов), `layout`/`typeset` (структура и чтение), `clarify`/`onboard` (подписи и первые/пустые состояния), `adapt`/`harden` (узкие экраны, ошибки, i18n) и `polish` (финальный проход). `critique` и `audit` можно применять как дополнительные проверки, но отдельный модельный code review автоматически не запускается.

Для подготовки этого ТЗ установка не нужна, и локальная копия Impeccable не создавалась. Официальный README поддерживает ручную project-local копию `.agents/skills/impeccable`; ручное копирование не устанавливает hooks/subagents. Launcher может скачать движок за пределы проекта в `~/.impeccable/bin`, поэтому перед его запуском нужно проверить возможность хранить этот движок внутри `temporary/` или продолжать без CLI. Live-режим не входит в текущий план: README описывает fallback для применения изменений с отключёнными проверками разрешений; отключение telemetry также не исключает запрос каталога визуальных направлений. Для этой работы достаточно прочитать skill/reference и хранить материалы в `temporary/`, если понадобится локальная копия.
